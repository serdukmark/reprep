# MAX: подключение утром в три этапа

Статус 20.09.2026: код авторизации, webhook, очередь ответов и клиентский Bridge реализованы. Проверены локально на синтетике, включая iframe и намеренно повреждённую подпись. **Реальные MAX API, сертификат, регистрация и мобильный/web-клиент не проверены. Ночью ни один запрос с токеном MAX не выполнялся.**

## 1. Владелец даёт бот и доступный HTTPS-адрес

Нужны токен выданного команде бота и домен, уже направленный на согласованный сервер с портом 443 и полной цепочкой доверенного TLS-сертификата. Самоподписанный сертификат/localhost не подходят. В настройках бота на платформе MAX указать URL MiniApp `https://ВАШ-ДОМЕН/` и кнопку открытия. Пример reverse proxy — [nginx-max.conf.example](../infra/nginx-max.conf.example); он не устанавливался и не публиковался ночью.

MAX MiniApp — обычный HTML/JS-клиент, прикреплённый к боту; самостоятельно вне бота он не закрывает кейс. [Подключение MiniApp](https://dev.max.ru/docs/webapps/introduction).

## 2. Заполнить две основные переменные и запустить

В существующем .env, не перезаписывая OpenRouter:

```dotenv
MAX_BOT_TOKEN=
PUBLIC_BASE_URL=https://ВАШ-ДОМЕН
```

Следующие команды **только утром после разрешения внешней интеграции**:

```sh
.venv/bin/python scripts/setup_max.py --apply
bash scripts/demo.sh
```

setup_max.py получает ID бота через GET /me, записывает MAX_BOT_ID, MAX_BOT_ENABLED=true и MAX_OUTBOUND_ENABLED=true в локальный .env, не печатает токен. Сама подписка пока не создаётся. demo.sh собирает/запускает Compose и ждёт healthcheck. Если разворачиваем на сервере без .venv, сначала выполнить установку Python-зависимостей из README; это предусловие, а не скрытая автоматическая установка.

Без `--apply` setup_max.py только проверяет наличие токена и формат адреса, **не обращается в сеть**. Наличие HTTPS в строке не доказывает доступность домена.

Актуальная документация указывает API `https://platform-api2.max.ru` и необходимость доверять сертификату Минцифры. Если цепочка не доверена стандартным хранилищем, владелец должен предоставить проверенный PEM bundle и указать MAX_CA_BUNDLE (путь, доступный процессу/контейнеру). TLS verification никогда не отключается. Две переменные достаточны только при уже готовой сети/TLS; код не создаёт домен, бот или доверие CA автоматически. [MAX API](https://dev.max.ru/docs-api/methods/POST/messages).

## 3. Зарегистрировать webhook и проверить внутри MAX

После появления HTTPS и запущенного приложения:

```sh
.venv/bin/python scripts/setup_max_subscription.py --apply
```

Команда подписывает на bot_started и message_created endpoint `/api/max/webhook`; секрет заголовка выводится из токена отдельным HMAC-purpose, либо задаётся MAX_WEBHOOK_SECRET. Никакие подписки не создаются автоматически при запуске сервера. Затем владелец сам открывает бота, нажимает Start или пишет /app: ответ должен содержать кнопку `open_app` для текущего bot ID. /help объясняет учебный цикл. Групповые сообщения, сообщения ботов и произвольные тексты игнорируются.

Открыть MiniApp, войти через MAX, убедиться, что появился «Аккаунт MAX». Проверить кнопку «Назад», закрытие с несохранённым текстом и вид на телефоне/web. Прогнать сценарий из [27_DEMO_SCRIPT_RU.md](27_DEMO_SCRIPT_RU.md).

Настоящие MAX-профили по умолчанию **не отправляют работы во внешний AI**: для этого требуется решение по данным. Для живого AI-показа синтетики доступны явно помеченные демо-роли внутри открытого MiniApp. Они не привязаны к MAX-личности и не заменяют проверку настоящей авторизации. Не включать demo в production; для закрытого демонстрационного стенда APP_ENV=demo, DEMO_ENABLED=true. Выбор режима — вопрос владельцу, а не молчаливое разрешение на настоящие ученические данные.

## Как устроена граница MAX

- Клиент загружает официальный Bridge с st.max.ru только при наличии параметров запуска MAX; берёт сырую initData, не initDataUnsafe. При отказе CDN остаётся проверка URL-строки, но нативные кнопки не гарантируются.
- InitData содержит auth_date, hash, user и, в зависимости от запуска, query_id/chat/start_param/ip. Сервер использует только проверенный user.id; имена, IP и полный запуск не сохраняются. Авторизация использует двойной HMAC-SHA256, дубли/повреждённое кодирование отклоняются. TTL 300 с — наше более строгое решение; после долгого онбординга приложение надо переоткрыть. [Валидация](https://dev.max.ru/docs/webapps/validation).
- BackButton подписывается/отписывается вместе с экраном. При несохранённом ответе включается closing confirmation; CSS учитывает safe-area. Методы ready/expand не выдумывались: в использованной документации они не заявлены. [Bridge](https://dev.max.ru/docs/webapps/bridge).
- Webhook подтверждает `X-Max-Bot-Api-Secret` timing-safe, отклоняет дубли заголовка и слишком старое событие. HTTP 200 означает постановку в постоянную очередь, не успешную отправку ответа. Приватные тексты/имена события не хранятся; сохраняются адресат и готовый стандартный ответ. Дубликаты определяются хешем канонического JSON.
- Исходящие ответы выключены без MAX_OUTBOUND_ENABLED. Попыток не больше трёх, нет сетевого запроса в обработчике webhook. При crash после отправки и до записи статуса возможен повтор ответа; exactly-once MAX API не предполагается.
- По документации webhook должен ответить за 30 с, TLS/443 обязательны; доставка повторяется, поэтому нужна дедупликация. [Подписки](https://dev.max.ru/docs-api/methods/POST/subscriptions).
- Встроенный CSP допускает Bridge и frame ancestors MAX/self; CORS wildcard не включён. Nginx не должен добавлять X-Frame-Options DENY/SAMEORIGIN. Реальные заголовки внешнего proxy ещё нужно проверить.

## Доказательства и ограничения

`tests/test_max.py`: замороженный вектор, независимо рассчитанный Node crypto; неверный пользователь/токен/кодирование/дубли/срок; endpoint авторизации и сохранение роли; webhook secret, дедупликация, команды, игнорирование групп, сетевой адаптер и предел повторов. `scripts/test_max_mutations.py` действительно запускает контрактный тест на двух намеренно испорченных реализациях и требует его падения.

`tests/browser/max.spec.ts`: эмуляция Bridge и локального iframe, настоящая серверная проверка синтетического initData, отказ подменённой личности, back и защита несохранённого ответа. CDN в тесте перехвачен локальным fixture — это **не настоящий клиент MAX**.

Не проверены: внешний TLS/CA, доставка MAX webhook, фактический формат события в командном боте, реальная кнопка open_app, политика публикации команды, мобильный/web MAX. Эти пункты требуют доступа владельца и остаются релизными ограничениями.

Дополнительный тест выполнен с **настоящим JavaScript Bridge**, скачанным 20.09.2026 с https://st.max.ru/js/max-web-app.js и поданным браузеру локально: 21 676 байт, SHA-256 `2897977d00ef66a4981ccb12f9e2ae8804a5007bb29ed2e39dfeb9369773d944`. Проверены чтение initData, исходящие события back/closing, отбрасывание back от чужого origin и обработка события с синтетическим origin MAX. Родительский MAX-клиент по-прежнему симулирован; это не доставка событий настоящего мессенджера.

В коде официального Bridge обнаружено использование sessionStorage без обработки запрета. Поэтому при запрете storage reprep не загружает Bridge и сохраняет вход через подписанную URL-строку с сессией в памяти. Нативные функции в этом режиме недоступны. Транспорт официального Bridge принимает MAX/oneme поддомены; CSP приложения допускает эти семейства для встраивания. Это сверка с публичным SDK, а не проверка всех хостов платформы.
