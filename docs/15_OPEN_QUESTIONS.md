### N-01. На каком HTTPS-домене и через какого MAX-бота показываем продукт?
- Почему владельцу: нужны командный доступ, выбор инфраструктуры и разрешение внешнего размещения; публикация ночью запрещена.
- Варианты: существующий командный сервер/домен — без новой подписки, но нужен доступ и TLS; отдельный VPS — платный тариф после выбора, отдельная эксплуатация; только localhost — 0 ₽, подходит для внутреннего просмотра, **не закрывает MAX-кейс**.
- Пока: **решила так, можно переиграть** — контейнер, MAX Bridge, API проверки подписи, защищённый webhook и очередь ответов, скрипты утренней регистрации; токен бота не извлекала в конфигурацию. Никакого деплоя/сообщений. После доступа: HTTPS, привязка MiniApp, запуск из MAX на мобильном и web, проверка реального init_data.

**Утренний маршрут MAX — один блок действий (код ночью больше не меняем):**
1. Передать токен командного бота через локальный .env и выбрать уже готовый HTTPS-домен/сервер. Нужны доступ к настройкам MiniApp, порт 443, полная доверенная цепочка TLS; при необходимости проверенный CA bundle. Без готовой инфраструктуры обещать десять минут нельзя.
2. В .env заполнить MAX_BOT_TOKEN и PUBLIC_BASE_URL; в кабинете MAX указать тот же URL MiniApp. Сохранить существующий OPENROUTER_API_KEY.
3. Из папки проекта: `.venv/bin/python scripts/setup_max.py --apply`, затем `bash scripts/demo.sh`, затем `.venv/bin/python scripts/setup_max_subscription.py --apply`. Это внешние действия, отложенные до разрешения владельца.
4. Открыть бота → /app → MiniApp: проверить «Аккаунт MAX», затем роли/сдачу/проверку, Back и закрытие с несохранённым ответом на телефоне и web. Для AI использовать только синтетическое демо до решения по данным.
5. Если не открывается: записать шаг и код ошибки без токенов; подробности только при необходимости — [инструкция](26_MAX_START_RU.md). Не отключать TLS-проверку ради запуска.

- Пока: **решила так, можно переиграть** — Qwen, hard max_price $1/M на вход и выход, 50 внешних попыток/UTC-день на базу; стоимость и ответы в 23_AI_MODEL_COMPARISON_RU.md. Превосходство Luna не установлено, она не подключена.

### N-05. Можно ли отправлять настоящие работы в OpenRouter и какой срок хранения?
- Почему владельцу: обработка данных детей, условия провайдера, согласия и права на материалы требуют ответственного за данные.
- Варианты: только синтетика — 0 ₽ юридического внедрения, без доказательства реального пилота; обезличенная работа взрослого преподавателя с согласованием — время на процедуру; реальный ученический пилот — согласия, политика, удаление/экспорт, возможные юридические расходы.
- Пока: **решила так, можно переиграть** — AI_SYNTHETIC_ONLY=true, AI_DATA_APPROVED=false. Для настоящего MAX-аккаунта внешняя AI-проверка заблокирована; ручная работает. Выгрузка прогресса есть, полного удаления аккаунта/согласий/retention-job пока нет. data_collection=deny не считается разрешением на данные детей.

## P1: обратимые продуктовые решения

### N-06. Какой предмет и тип работ демонстрируем первым?
- Почему владельцу: соответствие первому клиенту и сильному сценарию команды.
- Варианты: математика с числами/выбором/коротким объяснением — уже реализовано, 0 дополнительных дней; русский с развёрнутым текстом — нужны предметные рубрики и оценка; фото рукописи/OCR — платный мультимодальный этап и отдельная проверка распознавания.
- Пока: **решила так, можно переиграть** — математика, три текстовых типа, до 20 заданий. Фото, OCR и файлы не притворяются работающими.

### N-07. Когда ученик видит объяснение и когда может пересдать?
- Почему владельцу: педагогическая политика и нагрузка преподавателя.
- Варианты: после подтверждения — безопаснее, ожидание человека; подсказки преподавателя сразу — меньше тупиков; полный AI-разбор сразу — быстрее, риск показать неверное объяснение.
- Пока: **решила так, можно переиграть** — after_review по умолчанию; hints_first показывает только заранее написанную подсказку преподавателя. Новая попытка только после возврата, начинается с прежних ответов; исходники прошлых попыток сохраняются и доступны в истории. Опубликованное задание неизменно, редактирование через копию. Дедлайн информационный, не блокирует сдачу. Несданный черновик доступен только ученику; преподаватель получает отправленный оригинал.

### N-08. Нужны ли обе роли на одном MAX-аккаунте?
- Почему владельцу: зависит от клиента и UX онбординга.
- Варианты: одна роль — проще, уже работает; переключение ролей — новые права и тесты; отдельный администратор — больше сущностей и ответственности.
- Пока: **решила так, можно переиграть** — роль выбирается при первом входе, затем сервер её сохраняет. Приглашение одноразовое на 72 часа, код передаётся человеком; автоматических сообщений нет.

### N-09. Какую обвязку оставить в демо: расписание, материалы, оплаты?
- Почему владельцу: нужно выбрать ценность для репетитора, а не объём экранов.
- Варианты: весь текущий минимум — создание занятия, HTTPS-ссылки, ручная отметка оплаты; оставить только P0 — меньше демонстрационных переходов; подключать календарь/видеозвонки/эквайринг — доступы, комиссии и интеграционные риски.
- Пока: **решила так, можно переиграть** — только минимальная обвязка без внешних действий. Оплата вручную видна только репетитору; автопроверки переводов, видеоконференций, push-напоминаний нет.

### N-10. Кто проводит инженерное ревью и как вливаем в командный код?
- Почему владельцу: репозиторий командный; AGENTS.md требует ответственного инженера и тестовый стенд.
- Варианты: ревью ветки feat/reprep-mvp и PR утром — обычный review; выборочный перенос отдельных модулей — больше ручной интеграции; иной стек команды — сохранить API/fixtures, заменить реализацию, дороже по времени.
- Пока: **решила так, можно переиграть** — React/TypeScript + FastAPI + SQLite, один процесс/один контейнер. Локальная ветка и коммиты; без push/merge/main. SQLite — решение для демо, не обоснованный выбор для большой многопользовательской эксплуатации.

## Ночной аудит 24.09: обратимые решения

### АУД-Q1. Когда выкатить локальные исправления аудита на reprep.ru?

**Высший приоритет после AUD022/AUD025/AUD032/AUD035:** локально воспроизведены попадание задержанного ответа/экспорта прошлого аккаунта и восстановление прежнего кабинета из BFCache. Защита проверена локально; актуальные результаты — в docs/43_AUDIT_MORNING_RU.md; боевой инцидент этим не установлен. Нужно разрешение владельца на окно публикации после общего регресса, текущий ночной запрет deploy сохраняется.
- Почему владельцу: текущий запрос — безопасный аудит без изменения боевых данных; стенд продолжает работать на предыдущей версии.
- Варианты: (1) отдельное окно после полного регресса — дополнительных расходов нет, исправления попадут в показ; (2) после показа — расходов нет, найденные ошибки до этого останутся на стенде.
- Пока: **решила так, можно переиграть** — исправления только локально, без deploy/push. Проверки идут на синтетической базе.

### АУД-Q2. Нужен ли обязательный комментарий для жалобы на ошибочный или вредный разбор?
- Почему владельцу: это выбор между быстрым сигналом ученика и полезностью данных для разбора жалобы.
- Варианты: (1) оставить необязательным — 0 дополнительных затрат, сообщение можно отправить одним выбором категории; (2) требовать несколько слов для жалоб — ориентировочно 1–2 часа разработки и регресса, меньше пустых сообщений, больше действий ученика; (3) просить пояснение после отправки — ориентировочно 3–4 часа, потребуется отдельное состояние диалога.
- Пока: **решила так, можно переиграть** — сохранила текущий контракт: комментарий необязателен во всех категориях. В аудит включена проверка пустого комментария, это не считается дефектом.


### АУД-Q3. Нужно ли разрешать продолжать ввод во время сохранения новой формы?
- Почему владельцу: это необязательная настройка удобства для медленной связи; блокера демо нет.
- Варианты: (1) блокировать поля до ответа или таймаута — без новых расходов, нельзя случайно потерять правку; (2) сохранять отдельный буфер последующих правок — ориентировочно 2–4 часа разработки и регресса, можно непрерывно печатать, но сложнее различать сохранённую и новую версии.
- Пока: **решила так, можно переиграть** — формы пространства, занятия и материала блокируют поля во время запроса, по аналогии с ответами ученика. При ошибке поля снова доступны и содержимое остаётся. Это локальное исправление AUD019, на production не выложено.

24.09, обратимое решение аудита: несохранённые групповые формы теперь предупреждают о переходе, как остальные редакторы. Решила так, можно переиграть: подтверждение потери ввода без стоимости хранения; альтернатива — автосохранение локального черновика, потребует отдельного дизайна приватности между аккаунтами. Ночью добавлено только предупреждение (AUD027), владелец не блокирует проверку.

AUD028: то же обратимое решение о предупреждении применено к имени и настройкам напоминаний; сохранение одной формы не должно скрывать несохранённую другую. Без денег/доступов, можно переиграть. Ночью подтверждено тестами, не опубликовано.

AUD032 — обратимое решение аудита: при восстановлении документа из BFCache заново загружать приложение и проверять сессию, предварительно скрыв старый экран. Решила так, можно переиграть. Дополнительных денег/доступов не нужно; цена — возврат к стартовому экрану и необходимость сети. Альтернатива — выборочное восстановление дерева/черновиков после сверки сессии, ориентировочно 3–5 часов и дополнительный регресс приватности; до показа не усложняла. Выкатка остаётся в АУД-Q1, ночью не разрешена.


Дополнение к АУД-Q3 (AUD033): решено так, можно переиграть — комментарий и категория отзыва блокируются, пока сервер отвечает. Иначе поздний успех стирал новый ввод. Денег/доступов не нужно; альтернатива с отдельным буфером последующих правок остаётся в существующем вопросе.

AUD034: то же временное решение АУД-Q3 распространено на заявку ученика и ответ преподавателя в каталоге. Решено так, можно переиграть; дополнительного доступа или бюджета не требует.


### АУД-Q4. Как вести выход, когда сервер не подтверждает отзыв сессии?
- Почему владельцу: это обещание интерфейса о завершении сессии; сеть не позволяет гарантировать серверный отзыв.
- Варианты: (1) очищать текущую вкладку и честно предупреждать —0₽, уже реализовано; (2) оставлять вход до подтверждения —0₽, но данные остаются на экране, не рекомендовано; (3) отдельный механизм управления/отзыва сессий —ориентировочно2–4ч, без обязательных внешних расходов, требует отдельной проверки хранения реквизитов.
- Пока: решено так, можно переиграть — вариант1. Серверныйтокен может сохраниться при недоставленном logout; тесты проверили эту границу. Два параллельных выхода запрещены. Автоматическую очередь хранения старых токенов не добавляли.


### АУД-Q5. Когда объединить все переходы идентичности в отдельный session boundary?
- Почему владельцу: выбирать окноархитектурногорефакторинга перед показом; затрагивает приглашениепри входе и несданныеответы при401.
- Варианты: (1) оставить проверенные App/api/BFCache границы до показа —0₽ и без новых изменений поведения; (2) отдельный applySession/epoch/remount и полныйрегресс —примерно2–4ч,0₽ внешнихсервисов.
- Пока: решено так, можно переиграть — вариант1. Все setUser/setToken проверены по коду, нового воспроизведённого дефекта не найдено; инвентаризация и точные риски в docs44. Не считать этот анализ доказательством прохождения отсутствующих UI-тестов.
