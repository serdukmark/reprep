# Изоляция аккаунтов: углублённая проверка 24.09.2026

Проверки только в loopback headless браузере на синтетической базе. Боевой стенд не изменялся. Это не подтверждение живой смены аккаунтов внутри MAX.

## Причины и общие границы

1. AUD022: успешные ответы запросов предыдущего аккаунта применялись после смены пользователя. Все JSON-запросы клиента проходят через `apps/client/src/api.ts`; там ответ сверяется с версией сессии. Версия меняется в setToken. Проверка стоит до возврата данных вызывающему коду. Отдельный fetch экспорта имеет такую же проверку перед созданием файла.
2. При logout корневой App очищает списки работ, отношений, уроков, материалов, прогресса и приглашений, текущую работу и выбор. Дочерние компоненты размонтируются при переходе к экрану входа.
3. AUD025 (этот проход): корневые буферы `inviteInput` и `alias` переживали logout. Новый ученик видел введённый предыдущим код приглашения; форма регистрации MAX/TG показывала прежнее имя. Красные UI-прогоны подтверждают оба случая. Очистка дополнена, также сбрасываются роль регистрации, toast, режим редактирования, меню, текущий раздел и ссылка на незавершённое копирование. Это обратимое исправление приватности, дополнительных денег/доступов не нужно.

## AUD032 — настоящий BFCache (обновление после прежних ограничений)

Стандартный Playwright запускает Chrome с `--disable-back-forward-cache` — прошлые проверки не покрывали кэш документов. Отдельный headless-запуск без этого флага подтвердил `pageshow.persisted=true`: преподаватель → другая страница → новая копия приложения → выход и вход учеником → два «назад» восстанавливали старый кабинет преподавателя с его списками. Скриншот просмотрен. Это локальное раскрытие ранее загруженного состояния, не доказанный боевой инцидент.

Первый harness ожидал `load` при goBack и получил timeout; для восстановления документа ожидание заменено на `commit`. Второй прогон дал реальное нарушение, annotation `bfcache-restored=1`. AUD032: `sessionLifecycle.ts` скрывает весь документ при pagehide.persisted и pageshow.persisted, затем reload загружает актуальный sessionStorage и проверяет /me. Старый React state и in-memory token больше не используются. Обычный pageshow без persisted не перезагружается.

bfcache-after1/1 passed; bfcache-mutation1/1 обнаружил отключённую защиту. Расширение: bfcache-roles-after **25/25**, в том числе 5 реальных восстановлений BFCache (преподаватель→ученик, ученик→другой преподаватель, родитель→ученик, коллега→ученик, та же сессия преподавателя). Все показывают новый проверенный экран; счётчик persisted положителен, старый экран в requestAnimationFrame не виден. Это ещё не подтверждает поведение настоящего MAX webview. Возврат через BFCache требует загрузки страницы и сбрасывает прежнюю позицию интерфейса; сохранённые серверные данные не меняются.

Мутации расширенного набора: bfcache-roles-mutation5/5 обнаружили отключение обработчиков; у каждой проверки annotation persisted=1. Четыре смены роли выявили старый кабинет, неизменённая роль выявила показ кэшированного дерева до повторной проверки сессии. Общий279 после AUD032 выполняется.

Просмотрен итоговый скриншот `bfcache-guardian-learner-confirmed.png`: после возврата отображается кабинет Саши, без прежнего родительского кабинета. Исходный снимок bfcache-commit-navigation также просмотрен: до исправления действительно показывался кабинет Алекса. Все имена и данные синтетические.

Восстановление BFCache без сети также проверено: history-offline-demo, persisted=1, вместо старого кабинета видна ошибка Chrome ERR_INTERNET_DISCONNECTED; после reconnect/reload показан текущий ученик. Это безопасный отказ, не работа приложения офлайн.

Последующее bfcache-history2/2: два back и два forward с новой сменой аккаунта между ними дают два реальных persisted-события и актуальный кабинет; logout из вкладки с копией того же токена заставляет восстановленную первую вкладку показать вход. Отличать это от отдельно созданных сессий: независимая сессия второй вкладки остаётся своей (demo-login4/4). Одновременные нажатия не проверялись.

## Проверка единой точки сброса (после AUD035)

Просмотрены все `setUser/setToken` в `main.tsx`: начальная загрузка `/me`, демо-вход, MAX/TG-вход, выход и сброс демо. Обновление профиля меняет имя того же пользователя. Очистка списков, выбранной работы и буферов находится в одном корневом `logout`. Проверка версии сессии в `api.ts` блокирует поздние JSON-ответы и экспорт. BFCache — отдельный кэш документа, требующий обработки `pagehide/pageshow` даже при едином сбросе React-состояния.

Более широкий рефакторинг не применён. При входе по `#invite` нужно сохранить код до принятия; при 401 во время сохранения — несданный ответ; при обновлении имени — открытый кабинет. Безусловная очистка на каждый 401 нарушит проверенный U005, а на каждый `setUser` — сохранность текущего экрана при изменении профиля.

План после выбора безопасного окна: разделить состояния загрузки, входа, истёкшей и отсутствующей сессии; выделить `applySession/clearAccountState`, размонтировать кабинет при смене идентичности и отдельно спроектировать буфер несданных ответов. Потребуется регресс приглашений, 401, смены ролей, профиля и сброса демо. Оценка — 2–4 часа без внешних расходов; вопрос АУД-Q5. Анализ кода не заменяет UI-проверки.

26.09 дополнительно проверены настоящий таймаут выхода (15 секунд, tutor/guardian, 2/2) и восстановление BFCache после недоставленного logout (2/2, `persisted=1`, без показа старого кабинета). Серверный токен при недоставке остаётся действующим — это честно показанное ограничение.
